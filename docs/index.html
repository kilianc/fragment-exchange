fx.js

Fragment-oriented navigation for server-rendered applications

The server already knows how to render the truth. The browser just swaps the parts that changed.

fx is a minimal JavaScript library that enables partial page updates without changing the foundational architecture of your application. One attribute. No build tools. No framework.

<script src="/fx.js" defer></script>

<a href="/reports" fx-target="#content">
  Reports
</a>

<main id="content">

</main>

Motivation

The cost of accidental complexity

Modern web development often assumes that client-side frameworks are the default choice, even for applications whose data flow and operational requirements are inherently server-centric. Engineering teams frequently carry the operational burden of front-end toolchains, dependency ecosystems, and dual-state architectures—despite not benefiting from the abstractions those systems were designed to provide.

Most internal systems, dashboards, and data-intensive applications do not gain meaningful leverage from client-side component frameworks. They carry a cost in toolchain maintenance, state duplication, divergence between client assumptions and server reality, dependency risks, and onboarding friction.

fx explores the opposite direction. Rather than replacing or overshadowing server-rendered HTML, fx provides a minimal mechanism for fragment updates that remains strictly subordinate to server output.

The baseline remains strong

Server-side rendering is simple, observable, and robust. It works with caching, load balancers, logs, and existing application logic. Engineers already understand it.

A full-page reload is correct and trivial; the challenge is the user experience cost when only a small portion of the document changed. fx addresses this gap with minimal machinery.

Server authority

All rendering originates from the backend. The server is the single source of truth for what the page should contain.

URL-driven state

The URL encodes the entire view state. Reload, share, or bookmark—the result is always deterministic.

Minimal API surface

One primary affordance. The operational model can be fully understood in minutes, not hours.

Failure safety

fx declines into ordinary navigation when needed. If JavaScript fails, the application continues to function.

Core Model

The operational model

fx is built around a single attribute: fx-target. The operational model is intentionally simple:

1

The server renders a complete HTML document.

2

A navigation event (click or form submit) triggers a request for the next document.

3

The returned document is parsed in memory.

4

The fragment associated with fx-target is extracted and swapped into the current DOM.

5

Browser history is updated.

6

Failure modes fall back to normal navigation.

This approach avoids virtual DOMs, hydration, and client-side state. The server remains authoritative; the browser is a display layer.

Link navigation

<a href="/settings" fx-target="#main">
  Settings
</a>

<div id="main">
  <!-- Content rendered by server -->
</div>

When clicked, fx fetches /settings, extracts #main from the response, and replaces the current #main. The URL updates. History is preserved.

If JavaScript is unavailable, the link functions normally.

Form submission

<form action="/search" method="GET"
      fx-target="#results">
  <input name="q">
  <button>Search</button>
</form>

<div id="results"></div>

On submit, fx serializes the form, constructs the URL with query parameters, fetches the response, and swaps #results.

The URL reflects the query state, enabling bookmarking and sharing.

Loading indication

<a href="/reports"
   fx-target="#content"
   fx-loading-target="#content">
  Reports
</a>

During the request, the element specified by fx-loading-target receives the class fx-loading. This enables CSS-based loading states.

The class is removed when the request completes.

Eager fragments

<nav id="sidebar" fx-hungry>
  <!-- Navigation, badges, status -->
</nav>

Elements marked fx-hungry are included in every fragment swap, regardless of the explicit target. This ensures layout-level components remain synchronized with server state.

Interval-based refresh

<meta name="fx-refresh"
      fx-interval="5000"
      fx-target="#metrics">

<div id="metrics">
  <!-- Live data -->
</div>

The meta tag instructs fx to poll the current URL at the specified interval and refresh the target fragment.

Timers are automatically cancelled on navigation or when the meta element leaves the DOM.

Reference

Complete API

Attributes

AttributeDescription
fx-target CSS selector(s) identifying fragments to replace. Multiple selectors may be comma-separated.
fx-loading-target CSS selector(s) identifying elements that receive the fx-loading class during requests.
fx-hungry Marks an element for inclusion in all fragment swaps. Requires an id attribute.
fx-interval On <meta name="fx-refresh">, specifies polling interval in milliseconds.

Runtime configuration

fx.timeoutRequest timeout (default: 10000ms)
fx.clickFallbackHandler for failed link navigations
fx.submitFallbackHandler for failed form submissions
fx.historyFallbackHandler for failed history navigations

Server protocol

Each request includes an FX-Target header containing the requested selectors.

The server may return a complete document (simplest) or only the requested fragments (efficient). Both approaches are valid.

Development helper

Include fx.dev.js during development. It provides console warnings for common issues:

  • Duplicate element IDs
  • Missing target elements
  • Hungry elements without IDs
  • Invalid refresh configurations
  • Nested target elements

Enable verbose logging with ?fx-log=true or fx.toggleLog(true).

Scope

Non-goals

fx does not provide components, client-side routing, reactivity, global state management, server-side rendering replacement, or template systems. These omissions are deliberate and central to the library's usefulness.

fx should not be interpreted as a replacement for richer client-side environments. It is deliberately unambitious. Its value lies in acknowledging that many applications do not need the operational surface of modern front-end systems.

Predictability

The backend remains the single source of truth. There is no divergence between client and server state.

Composability

fx does not claim ownership of the DOM. It coexists with other libraries and widgets.

Epistemic simplicity

Engineers can fully reason about the system. The entire library can be read in one sitting.
